# EV charging current control

## Multiple vehicles

Use **Add vehicle** to save another vehicle, even when one is already configured. Each profile has a name, charger, battery sensor, usable capacity, and efficiency. **Edit vehicle** edits the selected profile. Profiles persist on the server; existing automatic or manual charger pairings remain visible and are preserved when adding profiles. The vehicle picker selects the plan, with departure and charge limit remembered separately in this browser for each vehicle.

Several vehicles may share one charger (including its battery sensor when it reports the plugged-in car). Select the vehicle that is actually connected before applying its plan. A charger still serves one vehicle at a time; this does not schedule sequential charging sessions. Distinct chargers cannot share one battery sensor. Unavailable battery sensors can be assigned, but a live reading is needed to apply a plan. Adding or editing profiles does not start charging or send charger commands.

`PUT /api/homes/{homeId}/ev/vehicles` saves `{ "id": "client-generated-uuid", "name": "Family car", "chargerEntityId": "switch.virtual_ev_charger", "battery": { "sensorEntityId": "sensor.virtual_ev_battery_charge", "capacityKwh": 75, "efficiencyPercent": 90 } }`. Reuse a returned ID to edit a profile; repeat saves update the same profile. Home responses include `evVehicles`. Existing automatically derived profiles use their charger entity ID until saved. Pass `vehicleId` with the current command so its charge limit resolves against that vehicle. Unknown vehicle IDs and charger mismatches are rejected, and editing a vehicle cancels its pending plan.

## Departure planning

Open **EV charging** in the sidebar (`/ev-charging`). Once the charger current control and power sensor are paired in Settings, its battery percentage sensor and usable capacity are detected automatically when their entity IDs or friendly names identify the same vehicle. Common descriptive words such as “charger”, “battery”, “charge”, “virtual”, and “lab” are ignored. Matches must be unique in both directions; ambiguous or unrelated household batteries are not selected. Discovery does not grant charger control permissions.

Percentage discovery includes Home Assistant `sensor` entities with device class `battery` and unit `%`. Capacity discovery includes `sensor`, `number`, and `input_number` entities explicitly named as capacity, with `kWh` or `Wh` units; energy-consumption readings are not capacity. The lab's **Virtual EV Battery Charge** and **EV usable battery capacity** match automatically. Capacity is read from the lab, rather than assuming 75 kWh.

The page immediately uses the live readings. If capacity is missing, only capacity needs to be entered in the pencil **Edit vehicle** dialog; if the sensor match is missing or ambiguous, choose **Add vehicle** to assign the correct sensor. The dialogs open only when requested; Cancel, Close, or Escape discard unsaved edits. Manual vehicle settings take precedence until **Use automatic detection** is selected. Charging efficiency initially uses 90%. Automatic matches are recalculated from current discovery each poll; missing readings block applying instead of substituting another battery.

Choose a local departure date and time and a **Charge limit (%)**. The limit defaults to the vehicle’s observed target when available, otherwise 100%. The page calculates:

```
remaining kWh = usable battery kWh × max(0, target percent − battery percent) / 100
required amps = remaining kWh × 1000 / (hours until departure × watts per amp × efficiency)
```

The rate rounds **up** to the next supported step relative to the charger's minimum. It respects minimum and maximum current, using the largest supported step when the target charge is infeasible and showing the estimated battery percentage at departure. A battery at or above the target needs no additional charging; its stopping limit can still be applied without changing current. The departure and charge limit are remembered in this browser per home and charger; manual battery pairing and vehicle specifications persist on the server. Automatic pairings follow current discovery.

**Start charge** on the main card sends the calculated current and, when available, the vehicle’s charge limit through the validated command queue. After both settings are observed, it turns on the charger and waits for its on-state before confirming success. Start commands expire after 90 seconds. While the charger is already on, **Update charging** applies settings without requesting a restart. The compact card shows the charge rate beside the current battery level; the separate estimate panel has been removed. Home Assistant `number` and `input_number` percentage controls named as a target or limit are matched uniquely to the battery. The target is set and observed before the current is changed; unavailable or changed mappings cancel the request. Both values must match live readings before the combined command is confirmed. Combined requests expire after 60 seconds. Live readings refresh the estimate, but this first version does not continuously change current or schedule around prices. Battery sensors can be assigned and read while the charger is off. The current-only API can still adjust a stopped charger without turning it on. The page’s Start charge action explicitly starts it, including from standby or with no power reading. Finish estimates assume charging starts now, so a later start requires recalculating. If the vehicle does not expose a charge-limit control, the page asks you to set the same target in the vehicle. Unavailable charger state or battery/current readings, disconnected homes, pending commands, and devices without control permission block applying. Existing Smart Shutoff remains active and can reduce or interrupt charging.

Completion is a constant-rate estimate with charging efficiency, not a guarantee: battery taper, car-side limits, interruptions, and sensor accuracy affect the finish time. The realistic lab defaults to an 80% vehicle target and models taper. Its `input_number.lab_ev_target` is discovered automatically and updated when applying the plan.

Pairing API: `PUT /api/homes/{homeId}/ev/battery` with `{ "entityId": "switch.virtual_ev_charger", "settings": { "sensorEntityId": "sensor.virtual_ev_battery_charge", "capacityKwh": 75, "efficiencyPercent": 90 } }`. Use `settings: null` to remove the manual override and return to automatic detection. Home responses include `evBatterySensors`; each EV's `evBattery` holds its effective pairing with `autoDetected: true` for automatic matches and nullable `capacityKwh` when capacity is unknown. Sensor entries also include discovered `capacityKwh` and an optional `chargeLimitControl` with its entity ID, observed percentage, range, and step. Invalid or unavailable sensor states become `null`, never zero. Database upgrades add these fields without changing existing charger settings.

## Charger setup and load management

In **Device settings**, pair the EV's on/off switch with its power sensor, then choose its **EV charging → Charging current control**. This explicit pairing identifies the device as an EV; names alone never grant control. Home Assistant must expose a `number` or `input_number` entity measured in amperes (`A`) with valid minimum, maximum, and step attributes.

Set **Charger watts per amp** to the total charging power per amp across all phases: 240 for a 240 V single-phase charger, or 690 for a 230 V three-phase charger. For the included virtual EV, select `input_number.virtual_ev_current_limit` and use 240. Pair its switch with `sensor.virtual_ev_charger_power`.

The device row then shows the current limit and supports manual changes within the Home Assistant range and step. A permitted, connected EV is required. This changes the current limit without starting a stopped charger. Recent activity records requests, retries, cancellation, and observed confirmation.

With **Smart Shutoff enabled**, **medium or high grid outage risk**, and the EV set to **Anytime**, a fresh total at or above 11,000 W triggers current reduction before automatic shutoffs when the EV can continue charging within the available capacity:

```
other load = household watts − measured EV watts
available EV watts = 11,000 − 100 − other load
current = round down available EV watts / charger watts per amp
```

The result respects the charger's minimum, maximum and step, and is always lower than its current setting. At 6,000 W of other load, a 240 V charger drops from 32 A to 20 A: 4,800 W of charging and 10,800 W total. Requests use Home Assistant's `number.set_value` or `input_number.set_value` actions, and are confirmed from a subsequent observed current limit. One EV is adjusted at a time before replanning from measured household load.

If there is insufficient capacity for minimum charging, or its current control is unavailable, the existing automatic shutoff selection applies. Failed/unconfirmed current requests expire after 30 seconds and are not endlessly recreated during the same overload. Unknown household power pauses automation; unknown EV power prevents estimating a reduction. Never and Sometimes devices are never automatically throttled. Automatic reductions persist the original current limit and the last managed setting. Low grid risk permits usage above 11 kW and never initiates current reduction. Once capacity has been available for 5 seconds, the shared restore queue increases to the highest supported current that fits with 500 W of spare capacity, capped at the original limit. At low risk, the queue can restore the original current even when total usage exceeds 11 kW. Partial increases remain at the front of the queue; other eligible devices may proceed if no further amp increment fits. Only observed confirmation at the original limit removes the entry. Further reductions preserve the first original target. Manual changes, Keep current rate, and removing device access relinquish automatic current restoration. Failed increases remain visible without endless retries. A shut-off EV is first restarted at its reduced current, then its amp limit is restored. **Demo only:** device restart delays are 15 seconds off, 5 seconds of stable capacity, and 5 seconds between restorations. These are deliberately shortened from the production-oriented 2-minute/1-minute delays. This is a polling-based load-management feature, not an electrical protection mechanism.

API: `POST /api/homes/{homeId}/ev/current` with `{ "entityId": "switch.virtual_ev_charger", "amps": 20, "idempotencyKey": "unique-request-key", "chargeLimitPercent": 80 }`. Omit `chargeLimitPercent` for a current-only command. Pass `startCharge: true` to start the charger after confirming the requested settings. The default is false, preserving current-only callers. Requests with different start intentions cannot reuse an idempotency key. Settings accept `evCharging: { "switch.virtual_ev_charger": { "currentEntityId": "input_number.virtual_ev_current_limit", "wattsPerAmp": 240 } }`; `null` removes a pairing. Omitted mappings preserve existing configuration.

Home Assistant references: [Number actions](https://www.home-assistant.io/integrations/number/), [Input number actions](https://www.home-assistant.io/integrations/input_number/).
